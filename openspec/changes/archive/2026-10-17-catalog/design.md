# Design

## Context

ADR-0005 fixes SQLite (bundled `rusqlite`), WAL, one batching writer and read-only readers. ADR-0006/0007/0008
define what a source, a file fingerprint, a stage and a scan run are. ADR-0018 defines the ID-list query shape.
Budgets: ADR-0026. Secrets never go into the catalog (ADR-0031).

## Goals / Non-Goals

**Goals:**
- Crash-consistent checkpoints for resume; 50k rows/s; 1M ID list in 300 ms.
- A schema that later changes extend only through migrations.

**Non-Goals:**
- An ORM; full-text search (AI keyword search uses simple `LIKE`/JSON for v1).

## Decisions

- **Location.** `directories::ProjectDirs("app", "PhotoSquirrel", "PhotoSquirrel").data_dir()/catalog.db`;
  override with `--data-dir` (CLI) or `PHOTOSQUIRREL_DATA_DIR` (tests, CLI, app). `thumbs.db` lives beside it.
- **Pragmas.** `journal_mode=WAL`, `synchronous=NORMAL`, `foreign_keys=ON`, `temp_store=MEMORY`,
  `mmap_size=256MB`, `cache_size=-65536` on the writer; readers open with `SQLITE_OPEN_READ_ONLY`, `query_only=1`.
- **Migrations.** `ps-catalog/migrations/NNNN_name.sql` embedded with `include_str!`, applied in one transaction
  each, `user_version` bumped in the same transaction. A `tests/fixtures/catalog-v1.db` is generated by a test
  helper (not committed) from migration 1 only.
- **Schema v1.** `source(id, root_path, volume_uuid, device_hint, total_bytes, fingerprint BLOB, status, added_at)`;
  `file(id INTEGER PRIMARY KEY, source_id, rel_path, size, mtime_ns, file_index, stage, class, reasons JSON,
  content_id BLOB, identity_kind, phash, dhash, hash_version, width, height, capture_ts, capture_provenance,
  format, metadata JSON, attempts, missing_since, UNIQUE(source_id, rel_path))`; `scan_run(id, status, started_at,
  ended_at, sources JSON, stats JSON)`; `file_error(file_id, run_id, stage, message, at)`. Sort-key covering
  indexes: `(class, capture_ts, id)`, `(source_id, rel_path)`, `(content_id)`.
- **Writer (`ps-catalog::writer`).** A dedicated thread owning the write connection, fed by a bounded
  `crossbeam-channel` of `Command` enums (`UpsertFiles(Vec<FileRow>)`, `StageResult{...}`, `RunStatus{...}`,
  `Flush(oneshot)`). Batches up to 2,000 rows / 100 ms (ADR-0005), prepared cached statements, one transaction
  per batch. Submitters get errors via an error channel and `Flush` acks.
- **Readers (`ps-catalog::read`).** A pool of 4 read-only connections (`parking_lot::Mutex` per slot).
- **ID list.** `SELECT id, sort_key FROM file WHERE <filter> ORDER BY <sort>, id` streamed into
  `Vec<ItemId>` (u32) + `Vec<[u8;16]>`; the sort key packs (primary key 8 bytes big-endian, id 4 bytes, 4 bytes
  group/flags) so the timeline scrubber can binary-search it (ADR-0018). Filters are a typed `ps-model::Filter`
  compiled to SQL with bound parameters only.
- **Benches.** `ps-catalog/benches/catalog.rs`: insert 1M rows; ID list over 1M. Registered in `perf-budgets.toml`
  as `catalog-insert` (µs per row, max 20) and `catalog-id-list-1m` (ms, max 300); throughput budgets are
  stored as time per unit because `cargo xtask bench` budgets are upper bounds.

## Risks / Trade-offs

- [WAL growth during long scans] -> `wal_autocheckpoint` default plus a passive checkpoint after each run.
- [1M-row ID list memory] -> 20 bytes/item = 20 MB, within ADR-0018's estimate.
- [Kill test flakiness] -> the consistency check is deterministic regardless of kill point; the kill point is seeded.

## Verification

- `cargo bench -p ps-catalog --bench catalog`, `cargo xtask bench --check`.
- `cargo xtask ci`, `openspec validate catalog --strict`.
